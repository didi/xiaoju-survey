你正在为当前仓库建立一套 AI-agent-friendly 的工程结构，用于同时服务 Cursor、Claude Code 以及未来其他 coding agents。

目标不是生成一堆文档，而是建立一套"对下一次 agent 仍有高价值的信息结构"。

必须遵守以下架构原则：

1. `AGENTS.md` 是跨工具导航入口，只做导航，不做百科全书。
2. `CLAUDE.md` 是 Claude Code 的薄适配入口，不重复正文，优先通过 `@path` 导入关键文件。
3. `harness/` 是长期知识层，放长期有效的项目知识、workflow、边界、不变量、质量要求。
4. `work/` 是执行态工件层，放 PRD、技术方案、任务拆解、验证结果、运行日志等短中期内容。
5. `.claude/` 只放 Claude Code 专属适配内容，如 commands、skills、agents、settings。
6. repo 里保留"对下一次 agent 仍有高价值的信息"，不是保留"所有发生过的事情"。
7. 活跃计划留在 repo；完成计划退出默认上下文；有复用价值的内容蒸馏回 `harness/docs/`；纯历史弱化可见性或指向外部系统。
8. 不允许把猜测写成事实。任何无法从代码、现有文档、配置、脚本直接确认的信息，都标记为 `TODO: needs input`。
9. 优先复用现有仓库中的 README、docs、脚本、CI 配置、package.json 等现有事实来源。
10. 如果用户提供外部开源文档链接，把它们视为参考来源；若与当前代码事实冲突，以当前代码事实优先，并显式指出冲突点。
11. 需求交付遵循固定链路：
    PRD(work/requests/) → 技术方案(work/specs/) →
    任务拆解(work/tasks/) → 实现 → 自验证(work/evals/) →
    知识回灌(harness/) → 计划归档(harness/plans/recent/)
    每个环节都有对应工件，不要跳步。
12. 除文件路径、脚本名、命令名、代码标识符外，所有生成内容默认使用中文。
    对关键工程术语采用"中文 + 英文括号首提"的方式，例如：
    架构不变量（Invariant）、边界（Boundary）、技术方案（Tech Spec）。
    不要整篇英文，不要中英混乱切换。
13. 文档风格要求：
    - 面向中国研发团队，使用简洁、专业、工程化中文
    - 少空话、少概念堆砌
    - 用"规则 / 原因 / 例子 / 触发时机"这种结构表达
    - 不要翻译代码，不要翻译命令
14. 不要创建新的检查脚本目录（如 `scripts/checks/`）。检查能力通过文档化已有命令的组合来实现，不额外造轮子。
15. 避免文件冗余。同一类信息只在一个文件中维护。references/ 下只放纯外部链接索引，不与 engineering/ 下的使用指南重复。
16. 如果目标文件已存在，先读取现有内容，与新生成内容做 diff 对比。
    优先保留已有内容中的手工调整和项目特有信息，合并新增部分。
    不要无脑覆盖。冲突处标注 `<!-- CONFLICT: ... -->` 让用户决策。
17. 初始化完成后检查 `.gitignore` 是否已包含：
    - `.claude/settings.local.json`（本机权限配置，不进版本控制）
    - `work/runs/` 下的大文件（可选，视团队约定）
    如缺失，在 step8 自检中提示用户补充。

你输出时要遵循：
- 先盘点，再生成
- 少说概念，多落文件
- 生成的文件必须能直接写进仓库
- 不要发明不存在的命令、目录、服务或流程
